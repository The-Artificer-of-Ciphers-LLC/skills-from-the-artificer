## 1. Which hook events force Claude to continue without a human message

| Mechanism | Event | Exact output | Does Claude see it | Effect |
|---|---|---|---|---|
| Stop block | Stop | stdout JSON `{"decision":"block","reason":"<text>"}`, exit 0 (hooks:2601-2616) | Yes: "`reason` ... Tells Claude why it should continue" | Claude does not stop; a new model turn starts with the reason |
| Stop exit 2 | Stop | exit 2, text on stderr (hooks:848-861, :2616) | Yes: "Claude receives the stderr message as the explanation for why it should continue" | Same as block |
| Stop non-error feedback | Stop | `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"..."}}` (hooks:2620-2630) | Yes | Conversation continues; transcript labels it "Stop hook feedback", no hook-error notification; same loop protections |
| SubagentStop block | SubagentStop | same JSON / exit 2 (hooks:1019, :2601) | Yes (subagent) | Subagent cannot finish; continues |
| PreToolUse deny | PreToolUse | `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<text>"}}` or exit 2 + stderr (hooks:1797-1815) | Yes: "For `"deny"`, shown to Claude"; exit 2 "Claude sees the stderr message as the denial reason" | Only that tool call is blocked; the turn continues, Claude reads the reason as the tool result |
| PostToolUse block | PostToolUse | `{"decision":"block","reason":"..."}` (hooks:2020-2030) | Yes: "adds the `reason` next to the tool result"; original output still visible | Does not undo the tool; feedback only |
| additionalContext | SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, Stop, SubagentStop | `hookSpecificOutput.additionalContext` (hooks:935-1000) | Yes, wrapped in a system reminder, placed next to the tool result (or at end of turn for Stop) | Context only; 10,000 character cap, overflow becomes a file path plus 2,000 character preview (hooks:913-921, :996-998) |

Stop details (hooks:2539-2541): input carries `stop_hook_active`, "`true` when Claude Code is already continuing as a result of a stop hook. Check this value or process the transcript to avoid blocking on a condition that will never resolve." Claude Code applies an "8-consecutive-continuation cap": after eight consecutive stop-hook continuations, Claude Code "overrides the next block and ends the turn"; raise with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`. Stop does not run on a user interrupt; API errors fire StopFailure instead (hooks:2529-2536). SubagentStop input also has `stop_hook_active` (hooks:2390).

Loop avoidance, concretely: (a) if `stop_hook_active` is true AND the same unresolved condition is still present, either allow the stop or change the reason (do not repeat verbatim); (b) keep a persisted counter keyed by `session_id` and condition signature; (c) rely on the harness 8-continuation cap as the outer bound only. The repo's `subagent-output-cap.cjs:91,114` already does one-shot block honoring `stop_hook_active`; `run-incomplete-guard.cjs:434` blocks without checking it (per the existing analysis, section 5D).

`continue:false` (hooks:927-928, :935-940): `{"continue": false, "stopReason": "..."}`. "If `false`, Claude stops processing entirely after the hook runs. Takes precedence over any event-specific decision fields." `stopReason` is "Message shown to the user ... It stays in the conversation, so Claude sees it if the conversation continues". For PreToolUse/PostToolUse "the stop applies even when the tool call fails or completes while Claude is still streaming". This is the hard halt and must NOT be used for the breaker: it ends the turn, and the docs describe no hook or automatic way to resume it. The turn only continues if something else starts a new turn (a human prompt, `/goal`, a scheduled wakeup, or an external `claude --continue`/`--resume`). I inferred "needs a human restart" from the absence of any documented resume path; the docs only say Claude "stops processing entirely".

Verified in this repo: no hook uses `continue:false` (existing analysis section 1). The halts are text: the breaker backstop (`guard-denial-breaker.cjs:272-282`, "Stop now. Tool calls are disabled until the user replies.") and guard denial texts that say to stop.

## 2. Can a hook inject a user turn or restart a halted session?

Supported:
- Stop (or SubagentStop) `decision:"block"` / exit 2 is the supported "automatic restart" of the current session: it starts another turn with `reason` as the instruction. Bounded by `stop_hook_active` and the 8-continuation cap (hooks:2541).
- `/goal` (https://code.claude.com/docs/en/goal) is a built-in session-scoped Stop hook: "Claude keeps working toward it without you prompting each step". It clears on met/impossible/unfixable error. The goal page's comparison table lists a Stop hook as "The previous turn finishes" to "Your own script or prompt decides".
- SessionStart `initialUserMessage` (hooks:1168): "used as the first user message of the session. Applies in non-interactive mode with the `-p` flag, where it becomes the first turn even if no prompt is provided ... creates the turn". Only at session start and only with `-p`.
- External driver: `claude -p "<prompt>" --resume <session_id>` or `--continue` (headless.md:351-371) starts a new turn in a prior session from a script. A hook can only do this by spawning a detached process; it is not a documented hook feature.
- `PermissionDenied` hook: `retry: true` tells the model it may retry a denied call (hooks:~2237, decision table line 1031-area). Applies to auto-mode classifier denials only, not hook denials.

Not supported (no documentation found): a hook field that injects a user-role message mid-session; a hook that un-halts a `continue:false` turn; `additionalContext` on an idle session (it is only attached to a tool result, prompt, SessionStart, or Stop end-of-turn). UserPromptSubmit `additionalContext` fires only when a prompt is submitted, so it cannot fire by itself.

Conclusion: the correct automatic "restart" is a Stop-hook block (plus PreToolUse deny-with-remedy in the middle of a turn). Never `continue:false`, never an all-tools deny.

## 3. Detecting Memtrace quota exhaustion

What this machine shows (no memtrace docs page for it was found via `memtrace --help`, which has no quota text; evidence is from the binary and a real transcript):

Strings in `memtrace` (crates/memtrace-mcp/src/quota.rs), in order: `Daily throttle active (`, `/day after free roof). Upgrade at `, `Daily query limit reached (`, `/day). Upgrade at `, `Monthly query limit reached (`, `). Upgrade at `, `/api/quota/consume`. Also `') refused the call on its query quota: ` (multi-store routing path) and `quota_exceeded`. Auth lapse text: `Authentication expired. Run `memtrace auth login` to resume embeddings and quota sync.`

Real MCP tool result (transcript `~/.claude/projects/-Users-trekkie-projects-coincert/16f6699b-31c0-4755-ba76-8b2c81b52e0e.jsonl`, `tool_result` text content, minimal fields):
```json
{"error":"quota_exceeded","message":"Monthly query limit reached (21806). Upgrade at https://www.memtrace.io/pricing","quota":{"blocked":true,"dailyLimit":null,"dailyUsed":0,"effectiveMonthlyLimit":21806,"monthlyLimit":20000,"monthlyUsed":21841,"periodEnd":"2026-09-20T00:21:18.000Z","plan":"pro_plus","stressLevel":"blocked","throttleMode":false,"upgradeUrl":"https://www.memtrace.io/pricing","warnAtPct":80}}
```
Detection keys, strongest first: JSON `error === "quota_exceeded"`; `quota.blocked === true`; `quota.stressLevel === "blocked"`; message prefix `Monthly query limit reached` / `Daily query limit reached`. `throttleMode:true` with `Daily throttle active (` means degraded, not blocked.

How it reaches hooks: in that transcript the record has no `is_error` field, so it arrived as a normal (non-error) MCP result. PostToolUseFailure fires only "when a tool that started executing fails: the tool threw an error, or an MCP tool returned an error result" (hooks:2087-2090), so it may NOT fire for quota. Do not depend on it. Use PostToolUse with matcher `mcp__memtrace__.*` (MCP naming and `.*` rule, hooks:355-370); PostToolUse input carries `tool_response` (hooks:2007). Treat `tool_response` as string or object (MCP output is "passed through without schema validation", hooks:2043-2053): stringify then `JSON.parse` the first text block. PostToolUseFailure input for MCP tools adds the `mcp_server` object plus top-level `error` string and `is_interrupt` (hooks:2097-2130); match the same strings in `error` as a second path.

Existing repo detection: none. `memtrace-first-guard.cjs` has no quota detection; the only mentions are prose in the deny text (`:1240`, `:1259-1260` "Memtrace unavailable / quota-exhausted? Use CodeGraph") and a comment/text in `memtrace-capable-dispatch-guard.cjs:72-79`. The guard therefore cannot know quota state; Claude has to infer it. A PostToolUse detector must write a state file (e.g. `~/.claude/state/memtrace-quota.json` `{blocked:true, until: periodEnd, session}`) that memtrace-first-guard reads.

## 5. Worktrees

How Claude Code creates and owns them (wt.md):
- `--worktree <name>`: `.claude/worktrees/<name>/` on new branch `worktree-<name>` (wt.md:21). `EnterWorktree` tool: creates one mid-session or switches to an existing one under `.claude/worktrees/` (wt.md:41-43). Subagents with `isolation: "worktree"` get a temporary worktree (wt.md:101-116). Claude Code writes a marker into the git metadata of every worktree it creates (wt.md:134).
- Hooks: `WorktreeCreate` (replaces default git creation; command hook prints the path as last stdout line; input `{session_id, transcript_path, cwd, hook_event_name, name}`; hooks:2935-2990) and `WorktreeRemove` (input adds `worktree_path`; exit 0 = removed; non-zero fails removal if directory still exists; JSON discarded; hooks:2993-3040). WorktreeRemove fires on exit of a `--worktree` session, subagent finish, background-session delete.
- Claude Code's own cleanup: on exit of an interactive session a clean unnamed worktree is removed, a worktree with work prompts (wt.md:54-58). A periodic sweep removes subagent/background worktrees older than `cleanupPeriodDays`, but "leaves a worktree in place" if it holds work, if it "belongs to a `--worktree` session you haven't backgrounded, whatever its age", or if you made it yourself with `git worktree add` (wt.md:124-134).
- Safe liveness signal, documented: "While an agent is running, Claude Code holds a `git worktree lock` on its worktree so that concurrent cleanup can't remove it" and the same for a backgrounded session; the sweep releases a lock whose session process has exited (wt.md:136-138). `-p` runs leave their lock in place until a later sweep (wt.md:60). Limit: the docs state the lock for subagent and background-session worktrees; they do not state a lock for an interactive `--worktree`/`EnterWorktree` main session (that case is protected by "not backgrounded" in the sweep, not by a lock). So a lock is sufficient but not necessary evidence of liveness.

Why `worktree-reap.sh` can delete an ACTIVE worktree (`claude-guards/hooks/worktree-reap.sh`):
1. Triggers: PostToolUse:Bash filtered `if: "Bash(git merge*)"` and SessionStart (`README.md:36`; header `worktree-reap.sh:4-6`). README itself says the `if` filter "has been observed firing on non-merge Bash calls" (`README.md:175-178`), so it effectively runs after many Bash calls (every turn that uses Bash). It runs in the SessionStart of any session in the repo, including a different session than the one that owns the worktree.
2. Predicate (`:63-101`): not main checkout, has a branch, not default branch, path under `<toplevel>/.claude/worktrees/`, no `locked` marker file under `<common>/worktrees/<name>/locked` (`:84-89`), `git merge-base --is-ancestor <branch> main` (`:92`), and `git status --porcelain` empty (`:98`). Then `git worktree remove` + `git branch -d` (`:111-112`).
3. The flaw: a freshly created worktree branches from main, so its branch tip equals main, `--is-ancestor` is TRUE, and with no edits yet `status --porcelain` is empty. A brand-new, in-use worktree therefore looks exactly like a finished merged one. The lock check is the only liveness signal, and it only helps if Claude Code or the user set a lock: per the docs an interactive `--worktree`/`EnterWorktree` session is not documented as locked (wt.md:136), and `git worktree add` by hand (the worktree-guard text prescribes it, `worktree-guard.cjs:128-131`) takes no lock at all. It checks no process, cwd, or session.
4. Evidence on this machine: `~/.claude/hooks/worktree-reap.log` has repeated reap entries every ~15 minutes for `claude/circuit-breaker-hooks-14720f` (00:16Z, 00:31Z) and `claude/git-worktree-conflict-7ab520` (00:44Z, 00:45Z) on 2026-10-04, with `error: the branch '...' is not fully merged` on the following `branch -d` (git removed the worktree dir first, then refused the branch delete). `git for-each-ref` shows both branches currently point at 8c7d31a == main, i.e. zero commits: exactly the "new worktree equals main" case. The earlier analysis file (section 6 caveat) records the same worktree vanishing mid-session. The hook is currently disabled locally (`~/.claude/hooks/worktree-reap.sh.disabled`) but still ships in `claude-guards/hooks/worktree-reap.sh` and is listed as active in `README.md:36`.
5. Secondary: `worktree-guard.cjs` is not a reaper (PreToolUse Write|Edit|MultiEdit, denies code writes in the main checkout, `:145-185`). Its deny text tells Claude to create a worktree, which is what produces fresh zero-commit worktrees that the reaper then removes. It does not itself delete anything.

## 6. Recommendation

### A. Breaker (replace halt with automatic re-do)
Events and outputs:
1. PreToolUse `*` (keep `guard-denial-breaker.cjs`): on a trip, DENY ONCE with a concrete remedy (exit 0, `permissionDecision:"deny"`, reason below). On repeats of the same signature, deny with an escalated reason. NEVER an all-tools deny, NEVER `continue:false`, no "ask the user" wording. Delete the backstop (`guard-denial-breaker.cjs:69, :272-282`) and the HALT.md exemption.
   - Reason template: `GUARD-BREAKER RESTART: <guard id> denied <tool> <short input>. Redo this step now with: <exact replacement call>. Memtrace first; if quota is blocked use <CodeGraph equivalent>. Do not ask the user. Re-do the work from the last step that was not guard-denied, then continue the original task.`
2. Stop `*` (new, `guard-restart-stop.cjs`): the automatic restart when Claude tries to end the turn while the breaker has unresolved trips this turn (state file keyed by `session_id`: `{sig, count, lastTripTs, resolved:false}`).
   - Output: `{"decision":"block","reason":"GUARD-BREAKER RESTART: the previous step was denied by <guard>. Redo it: <remedy>. Then finish the original task."}` exit 0.
   - Loop guard: if `stop_hook_active === true` and no new tool call succeeded since the last block (state `progress=false`), allow the stop (print nothing) so the harness cannot spin; otherwise block again with a DIFFERENT reason (next compliant alternative). Cap own blocks at 3 per trip signature, below the harness cap of 8 (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`, hooks:2541). Mark `resolved:true` when any successful tool call of a different signature occurs, or on a new human message (detect with the existing `isHumanEntry`, `guard-denial-breaker.cjs:138-158`).
3. SubagentStop `*`: same block, using `agent_transcript_path` for progress detection. Keep `subagent-output-cap.cjs` one-shot semantics (`:91, :114`).
4. SessionStart: no restart ability (`initialUserMessage` works only with `-p`, hooks:1168); use only `additionalContext` to reload breaker state notes. Do not rely on it.
5. Fix guard denial texts that say "SAY SO TO THE USER and stop" (`memtrace-first-guard.cjs:1281`, `measure-dont-infer-guard.cjs:61, :776-777, :803`) to give the concrete replacement call; otherwise Claude stops on its own.

### B. Memtrace quota to CodeGraph routing
- PostToolUse matcher `mcp__memtrace__.*`: parse `tool_response`; if `error==="quota_exceeded"` or `quota.blocked===true` or message starts `Monthly query limit reached`/`Daily query limit reached`, write `~/.claude/state/memtrace-quota.json` `{blocked:true, until: quota.periodEnd, ts}` and return `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"Memtrace quota is exhausted until <periodEnd>. Use CodeGraph for all code discovery: codegraph_explore (find_code), codegraph_node file mode (get_source_window), codegraph_callers/callees/impact. Do not retry memtrace."}}`. Also register PostToolUseFailure with the same matcher and string tests on `error`, since quota may arrive as a non-error result (section 3).
- memtrace-first-guard.cjs: when the state file says blocked and not expired, make the deny reason lead with the CodeGraph row of section 4 and also allow the codegraph file-mode read as the sanctioned read (already supported), instead of naming Memtrace tools first. Expire state at `periodEnd` or after 1 hour and re-probe with one cheap `mcp__memtrace__find_symbol`.
- Use CLI `codegraph ... --path <worktree>` for subagents (no MCP guidance reaches them; deny text already says so).

### C. Worktree reaper liveness
Make `worktree-reap.sh` never delete unless ALL of: (1) the branch has at least one commit not on its creation base AND is now an ancestor of default (i.e. `git rev-list --count <default>..<branch>` is 0 AND `git reflog`/commit count since branch point is greater than 0; a zero-commit branch is "new", not "merged"); (2) clean status; (3) no `locked` marker AND `git worktree list --porcelain` shows no `locked` line; (4) no live process with cwd inside the path: `lsof +D <path>` is too slow, use `lsof -a -d cwd -F n 2>/dev/null | grep -F "n<path>"` (or `pgrep -f` of claude processes then `lsof -a -p <pids> -d cwd -Fn`), skip if any match; (5) worktree directory mtime and `.git/worktrees/<name>/HEAD` mtime older than 24 hours; (6) never run it from the SessionStart/PostToolUse path of a session whose `cwd` is that worktree. Move the trigger to a periodic or explicit command; do not run per Bash call. Prefer deleting the hook in favor of Claude Code's own marker-based sweep (wt.md:124-134), which already refuses un-backgrounded `--worktree` sessions and hand-made worktrees. If the sweep is relied upon, set `cleanupPeriodDays` rather than keeping a custom reaper.
Also: make `worktree-guard.cjs` deny text recommend `claude --worktree`/`EnterWorktree` (Claude-owned, locked, markered) rather than raw `git worktree add`, so the harness's liveness protections apply.
